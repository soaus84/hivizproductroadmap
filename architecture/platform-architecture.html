Architecture overview
Platform layers
The platform is structured in four layers. Infrastructure at the base provides the runtime, storage, and async job execution. The core platform handles the data model, push/inherit/override propagation, notification delivery, and authentication. Workspaces are domain-bounded, configurable modules that clients enable. Intelligence surfaces — dashboards, pipelines, AI outputs — are the user-facing expression of workspace data.

The workspace model
Five workspaces
A workspace is a bounded, configurable domain. It has its own primary objects, its own maintenance interface, its own AI jobs, and its own layer on the worksite dashboard. Workspaces are enabled at the organisation level — a client pays for and activates the workspaces relevant to their maturity. The Field Intelligence workspace is always on. All others are optional.

All five workspaces
Complete triangulation. The platform knows: what was supposed to happen (management system), what controls should have prevented harm (risk), what people observed (observations), what went wrong (incidents), and whether the system itself is operating as intended (diagnostic). The Forge Works Map® classification becomes longitudinally trackable. Not survey scores — field evidence, incident evidence, verification evidence, and procedural evidence combined. The most precise organisational safety diagnostic available.

Propagation
Push · inherit · override
The push/inherit/override model governs how global standards propagate to sites. The same governance architecture applies across all workspace objects that have global and local variants: controls (Risk workspace), documents (Management System workspace), and in future any other globally-maintained standard. Global retains authority. Local variation is permitted within bounds — stricter only, never weaker.

Key design constraints
→ControlVerification and DocumentVersion are immutable on write. Corrections create new records. This is the integrity guarantee for investigations and regulatory use.
→DocumentRequirement is versioned. Linked to DocumentVersion.id — investigation AI can query requirements active on any given date.
→DiagnosticSurvey has hard anonymisation at data layer. responder_id is never stored. This is a schema constraint, not a UI setting.
→fw_factors, fw_confidences, fw_rationales are parallel arrays. factor[i] has domain[i], confidence[i], rationale[i]. Never scalar fields.

Build sequence
The roadmap arc
Each version introduces a new workspace or deepens an existing one. The workspace model architecture itself — workspace_config, layer system, AI context injection hooks — should be designed at V3 build time even though only one or two workspaces exist then. Retrofitting it costs significantly more than building it in.
V1 → V2
Field Intelligence workspace — full depth
V1: core loop (observation → insight → talk → action → visit). Offline-first. Context request loop. Pipeline stages. Worksite role slots. Enquiry (free text). V2: structured enquiry, manual insights, visit briefing pack, FW Map analytics, situational briefs, talk delivery obligations.

The platform a safety consultant would build if they had unlimited time and perfect data collection
From V1 through V6, every piece of infrastructure compounds. The observation enrichment pattern powers document ingestion. The push/override model powers the control register and the document library identically. The enquiry system powers document review. The async job queue powers every AI call across all workspaces. The worksite_id anchor means every workspace's data is immediately available to every other workspace's AI job without additional infrastructure.

The product gets smarter with each version not because new capabilities are added, but because each new workspace provides context that makes all the existing capabilities more precise. That's the architecture.
